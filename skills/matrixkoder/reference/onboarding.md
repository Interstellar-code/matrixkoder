# Onboarding wizard (first `/mk` in a repo)

Runs as pane steps in the dashboard's fullscreen pane, ten steps at 46 columns. When the pane cannot open (not fullscreen) the command answers with a read-only summary of what detection found, one line per block, ending `Nothing was written.` — there are no chat questions. Width is never a trigger; the mobile surface, which draws no Input or Select, gets a short notice instead of the steps. Every step is pre-filled from detection; the user edits only what is wrong. **One confirm at the end** — nothing is written before it. `/mk init <name>` is the same wizard with `<name>` as the project slug (normalised to `^[a-z0-9][a-z0-9-]{0,40}$`); `/mk setup` takes no name. Detection is read-only: `$.process.run` (`which`, `agy models`, `opencode models`, `herdr plugin list`, `codexbar`) and `$.fs` reads.

| # | Step | Detects | Answer lands in |
|---|---|---|---|
| 1 | Install mode | `--plugin-dir` dev folder vs marketplace install (info only) | nowhere |
| 2 | Data location | git root; `$MATRIXKODER_DATA` when set. Default is the repo's own `<repo>/.matrixkoder/` (`/.matrixkoder/` is added to the repo `.gitignore`), and the step offers `<globalDir>/projects/<slug>/` instead; a bare repo with no data dir and no build file starts in that home mode | `data_dir` in the settings file (`<data>/matrixkoder.yaml`, or `<data>/project.yaml` once the project is migrated); the repo `.gitignore`; the slug the root row is registered under |
| 3 | Agents | `claude`, `codex`, `opencode`, `agy` on PATH (`which`); `agy models` and `opencode models` plus `opencode models zai-coding-plan` and `opencode models ollama-cloud`; `herdr` + `herdr plugin list` | `agents` in the settings file; the herdr link choice drives the `herdr plugin link` call at the write |
| 4 | Usage | `codexbar --version` and `codexbar config providers`; enabled providers (every enabled one is pre-selected; zai joins when opencode is on the Z.AI plan, ollama when Ollama Cloud models are found); the z.ai key is entered by the user into CodexBar, never via the model | `usage` (`source`, `providers`) |
| 5 | Gates | package manager; install / test / typecheck / lint / format commands, all five asked as whole-repo runs (`pnpm exec vitest run`, `pnpm exec eslint .`, `ruff check .` — nothing expands `{paths}`/`{files}`, so none are proposed); baselines; server-starting commands | `gates`, `baselines`, `banned_commands` |
| 6 | Routing | builder order (default: the enabled agents, in policy order; a name that is not an enabled agent is named, not blocked); max build lanes (1-5); the two Claude reserve floors; the integration branch (`git symbolic-ref`, and a `feature/x` or empty one is named) | `routing_preferences` (`builder_order`, `max_build_lanes`, `reserve_floor.claude`); `repo.integration_branch` |
| 7 | Autonomy | builder permission-skip (yes/no; builders run in their own worktree only); the pre-authorised list | `autonomy_contract` |
| 8 | QA | frontend?, dev URL, start cmd (orchestrator only), themes, mockups dir, `qa.integration_target` (`local-main` = QA on the running dev server, or `branch`) | `qa` (the port is derived from the dev URL, never asked) |
| 9 | Dashboard prefs | auto-open, status chip, toasts, poll interval | the plugin's `userConfig` settings (`claude plugin configure matrixkoder`: `autoOpen`, `chip`, `toasts`, `usagePollMin`) — level `global` / home `userConfig` (C8), not yaml keys, and written at the step-10 confirm, not here |
| 10 | Review + confirm | shows the yaml as it will be written (see below) | writes the yaml, the project store and the root row; the step-9 prefs land in the plugin's `userConfig` |

Values the wizard does not ask are written as fixed defaults and never shown: `lanes` (`{ slots: 1, pattern: '../{repo}-mk-{n}', reuse: true }` — the cap is `max_build_lanes`), `routing_preferences.policy`, `effort_by_size`, `reviewer`/`visual_reviewer` (carried over when the replaced file has them), `autonomy_contract.pause_only_for`, `baselines` (`null`, `null`, `[]`). Open items go in as proposed defaults marked `# proposed`, never as extra questions.

Step 10 shows the whole file, scrollable, headed `exactly what is written` — its `checked_at` is the timestamp the write stamps, so nothing is `pending` and no line is cut. When a yaml already exists the keep/replace choice decides the form: keep (the default) draws that whole file, replace draws `-`/`+` rows against the file on disk with a `N lines changed · M unchanged` count. Write with `w`; nothing is written before that press.

On the press the wizard: reads every file it merges into (an unreadable one aborts with nothing changed) → `mkdir -p <data>/plans <data>/runs` → writes the yaml atomically (temp file + `mv`, `.bak` first when replacing) → appends `/.matrixkoder/` to `.gitignore` in repo mode → registers the project with `python3 scripts/mk-state.py project register --slug <slug> --repo <repo> --data <data>` → creates the project store with `python3 scripts/mk-state.py sync --project <slug> --data <data>` (the script that owns it; the store is `<data>/mk-project.db`) → sets the four dashboard prefs → links the herdr plugin if that was chosen. A project with a root `projects.db_path` set is MIGRATED, and its settings file is the C2 `<project>/project.yaml` — the wizard reads and writes that name, never a second `matrixkoder.yaml` beside it. The root `mk-overview.db` `projects` row records `slug`, `repo` and `data_dir`; only `mk-migrate.py --switch` sets `db_path`, and that column is what marks a project migrated.

When that write made the yaml (a create or a replace), `/mk setup` then runs `mk-config.py migrate --data <data>`: it fills in the `session:` / `picks:` / `lanes.default_agent` / reviewer keys a pre-migration file lacks and drops the dead yaml copies of plugin settings (`dashboard:`, `usage.poll_min` — the plugin setting is their only home, C8). A kept yaml is never rewritten, so the migration is skipped for it. A migration failure warns on the post-write line and never fails the wizard. Those lines are **written into the file with the schema defaults of that day**, so a later change to a default never reaches an already-migrated file — change the line, or delete it and migrate again to have the current default written back. `~/.matrixkoder/config.json` is retired. Every setting key declares a `level` (`global`/`project`) and a `home` (`userConfig`/`yaml`); every yaml key (including `lanes.default_agent`) is level project, and the existing `scope` field stays the Settings tab's UI category (C8).

Every run of `/mk setup` starts from step 1 and re-runs detection: there is no drift check that skips a configured project.
