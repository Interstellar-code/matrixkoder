# Onboarding wizard (first `/mk` in a repo)

Runs as pane steps in the dashboard; when the pane is not available (not fullscreen, < 144 cols) the same steps run as chat questions. Every step is pre-filled from detection; the user edits only what is wrong. **One confirm at the end** — nothing is written before it. Detection is read-only (run through `ctx_batch_execute`; only counts and names come back).

| # | Step | Detects | Answer lands in |
|---|---|---|---|
| 1 | Install mode | `--plugin-dir` dev folder vs marketplace install (info only) | nowhere |
| 2 | Data location | git root; the project folder `~/.matrixkoder/projects/<slug>/` is where project data lives (C2) — `/mk setup` always creates the project's `mk.db` here (file mode is dropped, C4). No repo dir is used. Data from the old repo-local layout is moved by `mk-migrate.py` (dry-run, copy, switch, rollback, archive) | the project's `project.yaml`; the root `mk.db` `projects` row (`projects.db_path` set = migrated; the root `projects` table is the repo→data_dir registry) |
| 3 | Agents | `herdr` + `HERDR_ENV`; `claude`, `codex`, `opencode`, `agy` installed + logged in; `agy models`, `opencode models` plus `opencode models <provider>` per paid provider (e.g. `zai-coding-plan`); Codex models from the provider's supported list, not `codex debug models`; Codex sandbox mode; codebase-memory probe (`list_projects` `root_path` match — full check in `loop.md` §Bootstrap) | `project.yaml` `agents` |
| 4 | Usage | `codexbar` on PATH (else show the install command); enabled providers; live probe per agent; z.ai key for the OpenCode plan is entered by the user into CodexBar config, never via the model | `project.yaml` `usage`; `~/.matrixkoder/usage.json` (first poll) |
| 5 | Gates | package manager, test / typecheck / lint / format commands, scopable-to-paths; measured baselines; server-starting commands | `project.yaml` `gates`, `baselines`, `banned_commands` |
| 6 | Routing | builder order, reserve floors, max lanes, effort by size, reviewers | `project.yaml` `routing_preferences`; `repo:` `lanes` — reusable worktree slots, one by default (`slots`, `pattern`, `reuse`; the cap is `max_build_lanes`) |
| 7 | Autonomy | pre-authorised list, pause list, builder permission-skip flags (lesson 27: the user may need a permission rule or start the pane) | `project.yaml` `autonomy_contract` |
| 8 | QA | frontend?, start cmd, dev URL/port, themes, mockups dir, `qa.integration_target` | `project.yaml` `qa` |
| 9 | Dashboard prefs | auto-open, status chip, toasts, poll interval | the plugin's `userConfig` settings (`claude plugin configure matrixkoder`: `autoOpen`, `chip`, `toasts`, `usagePollMin`) — level `global` / home `userConfig` (C8), not yaml keys |
| 10 | Review + confirm | shows the filled `templates/matrixkoder.yaml` as one diff; single question "Write these?" | writes the project's `project.yaml` (via `scripts/mk-config.py`) and the root `mk.db` `projects` row; the step-9 prefs land in the plugin's `userConfig`, not a file |

Steps 3–8 are the checks listed in `loop.md` §Bootstrap detection. Open items go in as proposed defaults marked `# proposed`, never as extra questions. Later runs skip the wizard and only drift-check.

After a write, `/mk setup` runs `mk-config.py migrate` once: it fills in the `session:` / `picks:` / `lanes.default_agent` / reviewer keys a pre-migration file lacks and drops the dead yaml copies of plugin settings (`dashboard:`, `usage.poll_min` — the plugin setting is their only home, C8). Those lines are **written into the file with the schema defaults of that day**, so a later change to a default never reaches an already-migrated file — change the line, or delete it and migrate again to have the current default written back. `~/.matrixkoder/config.json` is retired. Every setting key declares a `level` (`global`/`project`) and a `home` (`userConfig`/`yaml`); every yaml key (including `lanes.default_agent`) is level project, and the existing `scope` field stays the Settings tab's UI category (C8).
